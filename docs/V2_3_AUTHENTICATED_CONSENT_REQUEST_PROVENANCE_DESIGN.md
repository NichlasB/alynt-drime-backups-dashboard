## Decision and Approved Boundary

Prefer a closed client-local request adapter with three separate operations: protected intent issuance, authenticated command consumption, and authenticated read-only receipt reconciliation. Only that reviewed adapter may construct a future authenticated command. An arbitrary caller-provided `trusted` flag, actor ID, provenance string, serialized projection or enabled constructor must never become authorization.

Preparing consent is not authority activation. Even a future correctly authenticated grant leaves authority, dispatch and rollback execution disabled. This slice changes dashboard documentation only; uploader source is read-only. No LocalWP/site access, SQL, options, cron, credentials, permissions, hooks, UI, protocol, versions, release or deployment changes are approved here. No new secret, capability or remote permission is proposed. Initial support remains single-site; multisite/network administration is rejected until separately designed and proved.

## Request Boundary and Intent Issuance

Use client-local WordPress session authentication and current-site `manage_options`, not role names, remote signatures, pairing tokens or Schedule Apply opt-in. Require capability and scope before sensitive reads, issuance or receipt lookup, then check them again immediately before command handoff. WordPress nonces protect request intent, not authorization or one-use replay; the nonce result must be checked explicitly, and the application's short deadline independently enforced. See [official nonce guidance](https://developer.wordpress.org/apis/security/nonces/), [current_user_can](https://developer.wordpress.org/reference/functions/current_user_can/) and [wp_verify_nonce](https://developer.wordpress.org/reference/functions/wp_verify_nonce/).

The preferred future transport is a dedicated client-local admin action, with no unauthenticated equivalent. Do not add a REST/AJAX/CLI/dashboard bypass. Candidate issuance/consumption/reconciliation use distinct action domains. Issuance and reconciliation may use POST for bounded request bodies but are read-only; GET must never create identity/storage, migrate, grant, revoke or rebind. A missing/corrupt/unsupported ledger is an error, not permission to initialize it. Actual bootstrap is a separate explicit storage gate.

The capability-protected client-local page may issue a purpose-specific issuance nonce; the issuance POST must verify it before sensitive fact reads or minting a command envelope. Do not accept an arbitrary nonce-action string from the request. Bound each body to 4 KiB and allowlist fields before digest/JSON work. WordPress form integers arrive as strings: accept only bounded canonical unsigned decimal strings, range-check before converting, and reject signs, leading zeros except zero itself, floats, scientific notation, arrays and overflow. Internal command integers remain strict integers. No user-selected site/blog scope, public caching or cross-origin nonce delivery is allowed.

After authorization, issue a bounded envelope from authoritative site/ledger facts: server-generated command UUID, contract/purpose, fixed current site UUID, stored binding expectation, expected permission generation, server `issued_at` and `expires_at`. Maximum candidate intent window is 300 seconds for every newly submitted command. Grant additionally requires explicit affirmative preparation consent. Revoke issuance uses the current validated site's ledger and does not require old pairing, remote opt-in or grant eligibility; it must remain available after those are gone. Rebind refers to a separately reviewed new semantic context, not a posted arbitrary replacement binding. Do not generate identity, keys, enrollment or schedules during issuance.

Bind the action-specific nonce to a fixed-order, version-domain canonical digest of the complete envelope, including purpose, UUID, site, binding, expected epoch and both times. Generate it only after deriving those facts. On consumption, exact-validate and unslash the allowed scalar fields, reject extras/arrays/coercions, reconstruct the canonical action and verify against the current session. Treat echoed envelope fields as untrusted until verification, then independently reobserve current site/binding/epoch and time for a fresh transition. Never accept posted issuer, actor, capability, current clock, trusted projection, hash or provenance. Never silently substitute a newer epoch/deadline/command ID when contention occurs.

This nonce-bound envelope avoids a separate issuance option or HMAC secret; it does not make WordPress nonces one-use, shorten core nonce lifetime, or prevent an equally privileged plugin/DB writer from fabricating data. WordPress's session-bound nonce check and current capability are required even if the digest matches. Receipt/CAS fencing provides application idempotency. No nonce, cookie, session token, salt, raw request, verifier or unnecessary personal identifier enters durable receipts/logs/support exports. Nonce-bearing response bodies must be private and not shared-cacheable; mutation responses use bounded redacted codes and safe local redirects only.

## Separate Consumption from Reconciliation

| Operation/case | Candidate result and permitted work |
| --- | --- |
| Fresh preparation grant | Authenticate, verify grant-specific envelope/nonce, deadline, exact site/context/epoch and capacity, then one pure CAS transition/receipt. Consent may become preparing; authority remains false. No schedule, scan, queue or remote effect. |
| Fresh revoke | Authenticate and verify fresh closure-purpose intent against stored site/epoch without requiring an old grant nonce/session or still-paired remote context. One confirmed CAS clears consent; preserve unresolved owners/journals as draining. Failed/unresolved write may leave the old grant; never report disabled. |
| Fresh rebind | Separate authenticated closure intent and reviewed replacement context; close old consent before any separately authorized connection writer. No inherited grant or automatic regrant; no connection write is performed by this adapter. |
| Same retained ID and exact verified command | Observe current/superseded receipt without CAS or extending consent. Changed digest/purpose is a conflict. No fresh epoch or new request is synthesized. |
| Original grant nonce or 300-second window expired | Reject command consumption even if a receipt might exist. Offer a newly authenticated, independently nonce-protected receipt observation, not resubmission with a renewed grant deadline. |
| Lost acknowledgement after possible commit | Reconcile the original ID using current local authorization and a distinct read-intent nonce bound to site/ID. A retained receipt is observed only; if absent/unavailable, report not found/unresolved, not permission to replay or certainty of no commit. |
| Grant retry after revoke/rebind | Superseded observation or stale epoch; never restore consent. A receipt read returns no executable command or reusable grant token. |

Receipt reconciliation must authorize before lookup and derive the current site, not accept a posted site selector. It may identify a retained historical command in that same site's ledger after a binding change, but must not expose private envelopes, bindings or raw history. Observe from one validated authoritative snapshot, include a bounded non-permission outcome, and do not claim the observation remains current after return. A fresh authenticated reader need not be the original logged-in administrator: consent is site-owned, not a session lease. Logout/nonce expiry does not revoke an already committed grant. Automatic role-deletion/ownership-transfer revocation remains a separate lifecycle/writer gate.

The command adapter must perform authorization/intent checks outside pure CAS transformations and recheck authorization/context and the server clock/deadline at each attempted write boundary. Keep the original expected epoch for at most three attempts; contention reobservation classifies that request only. This bounds races but cannot make capability changes atomic with database CAS. Durable receipts acknowledge the ledger transition, not scans or secondary writes. Exceptions/ambiguous persistence stop dependent work and return fixed safe errors.

## Versioned Provenance Upgrade, Never Fixture Promotion

Do not change schema 4 to accept an authenticated-looking source string. Prefer a separately versioned strict successor in the existing dedicated non-autoloaded safety option, with a new authenticated-command digest domain and exact provenance validator. Its numeric version/field layout will be settled in the separately approved storage implementation, not assigned as a deployed contract here. Closed states have absent authenticated grant provenance; only a reviewed authenticated writer may create preparing-grant provenance in the same CAS as consent, epoch/revision and receipt. Provenance is a verified write-path claim, not a cryptographic signature or sufficient execution evidence.

Candidate migration is explicit and purpose-authorized, never automatic during issuance, getters, plugin startup or receipt reads. Require exact existing bytes/site/epoch, supported non-autoloaded source, valid clocks/counters and closure reserve. Preserve original due, native/terminal journals, dispatch ownership and unknown activation/handoff history. Unsupported/corrupt/absent state rejects without repair. A strict schema-3 or schema-4 fixture grant becomes closed with authenticated provenance absent, never relabeled or converted into a real receipt.

Keep schema-4 fixture receipts unchanged under a bounded, explicitly untrusted legacy namespace, with their original fixture digest semantics. Authenticated receipts are a distinct namespace/domain; cross-domain command-ID reuse is rejected, not observed as an authenticated duplicate. Do not erase retained fixture grants/closure evidence to make room. Account for both namespaces within the existing 128 KiB/depth-16 limits and reserve at least the existing closure byte/counter headroom; reject an oversized migration/new grant. Closure always retains its own last receipt and the grant being closed. No history pruning, epoch reset, optional-history eviction policy expansion or capacity relaxation is approved here.

Initially reject migration with unfinished work (including expired-but-unresolved claims/dispatch), rather than clearing or reassigning it. Authenticated successor closure will need lossless draining retention before that path can ship. A failed/ambiguous migration leaves the original row or an unresolved outcome; it is not disablement. Migration reruns observe a matching closed successor rather than erasing receipts or reopening it. Future empty-row bootstrap requires a separate explicit transaction contract and validated pre-existing site identity, never proof of never-activated history.

No reader upgrade occurs here. Schema-3 observer, two-field dispatcher and production legacy code remain incompatible/non-admitting. A future successor provider must require authenticated provenance plus independently proved current context, epoch, lifecycle/handoff and owned-effect fences; never infer history from `new_model`, clean journals, an empty option or a migration receipt. Deactivate/downgrade/uninstall must not silently restore legacy admissions over successor state.

## Focused Review and Implementation Gates

The focused design review separates five boundaries: capability/session authorization, server-issued purpose/deadline binding, receipt idempotency, versioned provenance/storage closure, and eventual owned effects. Replay and renewal cannot regrant; fixture metadata cannot become real trust; failed closure does not assert revocation; logs/exports retain no session secrets. Existing settings/connection whole-copy writers, off/on ABA, after-start checks, counter/storage failure, supported object cache, role/ownership changes, downgrade/handoff and multisite remain explicit unresolved gates. None is solved by authenticating a request.

| Next proof layer | Required evidence and boundary |
| --- | --- |
| Dormant request adapter foundation | Test-loaded/default-off issuance, consumption and reconciliation contracts; capability/nonce/time providers confined to explicit test adapters, not posted trust. Test guest/GET/no capability/wrong purpose/session/nonce, forged envelope/extra fields, expiry, stale epoch, no-read rejection and non-replaying outcomes. Injected checks prove contract logic, not actual WordPress sessions. No authenticated successor storage or production hooks. |
| Versioned closed provenance integration | Separately approved strict successor/migration and isolated owned SQL proof; preserve fixture history as untrusted, reject cross-domain duplicates, retain uncertainty/capacity and prove no fixture promotion or epoch reset. No actual site option migration or activation. |
| Actual WordPress request proof | Separately confirmed disposable Plugin Tester scope including necessary fixture users/storage cleanup. Real sessions/capabilities/nonces, denied requests, reauthentication after expiry, private receipt reads and interrupted acknowledgement; never certify this layer using mocked authorization. Actual options/cron untouched unless separately approved. |
| Production writers/ownership/lifecycle | Authoritative raw providers, conditional semantic writers closed first, stale timestamp and ABA adversaries, entry-point/after-start ownership fences, failure response and downgrade/handoff. Activation remains blocked until proved. |
| Release/activation | Applicable feature and full pre-release/security/lifecycle/package review followed by separately approved deployment and client-local enablement/pilot. Design/fixture CI is not active-feature clearance. Rollback execution remains separately gated and rejected. |

This is a focused source-backed design review, not execution of the full feature/pre-release workflow suite. That suite belongs before an integrated active feature is packaged for deployment, not as a substitute for the missing authorization/writer proofs. No runtime test is invented for candidate behavior: unchanged relevant regressions and source-reference/diff checks validate this documentation slice only.
