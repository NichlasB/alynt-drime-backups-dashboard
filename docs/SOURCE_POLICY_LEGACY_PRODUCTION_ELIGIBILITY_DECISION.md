## Explicit production trust proposal, requiring acceptance

The proposed production origin trusts the operator-controlled WordPress process,
loaded runtime and configured database service, with fixed known declaration
policy and fresh own-session readbacks. It does NOT pretend that an installed
host supplies the lab's image digest, CI job receipt or clean-worker guarantees.

| Property | Proposed production meaning / limit |
| --- | --- |
| Origin | Guarded code-owned composition from already bootstrapped trusted core/config AFTER capability, intent/types/revision and exact site-record admission. No request/option/env/receipt-selected model or constructor callback. |
| Source policy | Existing fixed core-library hashes/method origins, stock ambient identity, internal mysqli/mysqlnd, known cache/query registrations and approved observer policy. No current-hash self-learning, borrowed handle, unknown subclass/getter/autoload or arbitrary source-manifest argument. |
| Runtime/service trust | Trusted installed host/distribution and explicitly configured local database are assumptions. Exact version labels and readbacks are consistency gates, NOT server-binary provenance, immutable image identity, vulnerability clearance or malicious-host protection. |
| Qualification | A candidate row is not successful native/request evidence. Freeze changed code and prove the accepted deployment-matched cohort off production before wiring/release. Do not announce support for arbitrary rebuilds, other versions/transports or all WordPress/PHP permutations. |
| Security limits | No independent loaded-object/complete-ABI/host attestation or secure erasure. PHP private state/Reflection is not a security boundary against malicious code already executing in the same trusted process. No new attestation/key/toolchain infrastructure is selected. |

This is an explicit assurance choice, not inferred from the prior LAB-only trust
acceptance. It retains the application's existing trusted-host/configuration
assumption, while adding narrowly bound consistency/ownership checks. If the owner
does not accept this model, keep the candidate closed; do not silently weaken
guards or install a new provenance system. No trust-policy implementation now.

## Resolve the pre-connect/active circularity without a ready bypass

Source inspection finds that Trusted_Context::capture currently calls valid(),
which requires receiver->profile() active facts and the options binding. That is
correct for its disclosed already-bound isolated owner, but cannot provision a
fresh native owner which must be admitted BEFORE it allocates/connects. Calling
that method earlier, setting ready/facts manually or bypassing valid is rejected.

The selected next foundation must join two distinct checks in the SAME private
context/receiver/query ownership, not create an independent transferable grant:

1. **Capture for bootstrap:** after existing request admission, allocate only
   handle-free fixed objects; verify declaration/ambient/cache/observer origins,
   freeze trusted endpoint/storage/config and the one expected policy row. Bind
   exact receiver/Query_Context identities before allocation. This stage may
   validate pre-connect DATA without requiring active facts, but cannot authorize
   owner queries, publish ready, export a frame or return a write-capable handle.
2. **Initialize and observe:** existing fixed owner performs its genuine object-
   only initialization, no-reconnect setup, callback lease, bounded connect and
   exact raw identity/helper/session/schema checks. One bound expectation is
   consulted at bootstrap, session, final and active checks. No public selector,
   ready injection, copied proof Reflection composition, raw SQL callback, secret
   getter or generic frame/connection setter in runtime. Fixed internal handoff
   must preserve PHP visibility and return only fixed adapter/results, not secrets
   or raw receivers. No nonexistent private cross-class API is assumed here.
3. **Active admission:** only the actual successful initializer may establish
   active context from its own observed facts/receiver/Query_Context relation.
   Native_Adapter requires that active stage and revalidates before later effects.
   Pre-connect capture, a matching catalogue or supplied facts cannot substitute.
4. **Terminal:** revoke before fallible close, retain one-attempt owner cleanup,
   preserve foreign/ambient registrations and exact error handler; drop private
   secret references. Keep only non-secret identity/configuration projection for
   later consistency checks, not repeated password-bearing snapshots. Do not fake
   a password to satisfy an active validator, erase core constants, promise secure
   zeroization or treat unconfirmed cleanup as success. No replay/reconnect.

These phases are a proposed refinement, NOT current executable behavior. In
particular, early never-opened/unsealed callback refusal need not claim successful
physical release; prove zero allocation and honest ownership/cleanup state.
Keep the existing eight setup steps,20-second/16-credit initializer,2s connect/
3s read options,3s statement/1s lock limits and all controller/resource budgets.
No SQL catalog expansion, budget reset or new callback authority follows.

Observer/cache eligibility is also required. Current Trusted_Context implements
an empty non-query observer subset; this decision neither broadens it nor relabels
unknown installed hooks as qualified. Preserve existing nonempty-hook/cache
semantics and tests on their owning paths. Genuine request/profile qualification
must establish positive availability for the intended accepted graph, not pass
by always returning unavailable or silently removing saves on supported stacks.
An unresolved graph/source/profile gap blocks the later application switch.
