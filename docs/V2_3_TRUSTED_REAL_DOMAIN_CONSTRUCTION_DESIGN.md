## Fixed construction and request admission

The eventual owner is a final, non-subclassable request facade with private
construction and no caller-supplied auth, context, storage, transaction, clock,
nonce, source selector or enablement ports. Its trusted dormant construction
fixes the current single-site blog/table scope, two option names, core auth APIs,
UTC/UUID source, native backend, codecs and real nonce domains. Construction itself
is zero-IO; later explicitly invoked operations verify prerequisites. No automatic
factory registration in bootstrap, admin hooks, REST, AJAX, cron or CLI is part of
the foundation. PHP/database code with the same privileges is outside the sandbox
claim; private constructors are not protection against a compromised plugin.

Core authorization must freshly validate the actual local logged-in session and
current site-scoped `manage_options`, not a cached user, nonce alone, posted actor,
dashboard action signature or fixture truth predicate. Reject multisite, switched
blog/table scope, unavailable core dependencies and unsupported environments.
Never change users, roles, sessions, credentials or identity to make admission pass.

Fresh permission checks must cover both user capability metadata and current role
definitions, not merely a new current-user object backed by stale `WP_Roles` or
option caches. Preserve genuine core capability/filter semantics; do not replace
them with a raw Boolean or remove security callbacks. The real-provider proof
must establish supported cache freshness outside locks, including role-definition
changes. The earlier fixture's user-role-change case alone does not prove this.

Resolve an issuance bootstrap cycle explicitly: before private reads, the small
POST issuance form is authenticated and uses the reserved real action
`alynt_drime_backups_closed_writer_issue_v1:{blog_id}:{purpose}`. Blog ID and
installation auth context are server-fixed, not body fields; core's local session/
nonce scope is still required. This refines the earlier candidate UUID-based issue
action so no unauthenticated/defaulted UUID lookup is needed. After that guard,
read the existing settings UUID without generating it, bind it to the command,
read/validate safety state, then recheck auth/issuance nonce before minting intent.
Nonce creation on a future admin page is not approval to install that page now.

Build a coherent raw observation frame with repeated state/target reads and stable
site/table scope, exact state bytes/epoch and target bytes; changed observations
deny rather than combining facts from different commits. This is a freshness
check for cooperating monotonic writers, not a substitute for the locked checks
or protection against a nonparticipating privileged writer.

Retain `closed_writer_request_v1` and the exact purpose-specific field order and
string/size/decimal/UTF-8/once-unslashed rules in the earlier design, in a separate
real contract implementation. Real command/read action prefixes are respectively
`alynt_drime_backups_closed_writer_command_v1` and
`alynt_drime_backups_closed_writer_receipt_v1`, binding the complete typed envelope.
They never accept fixture nonce prefixes. Original lifetime is positive, at most
300 seconds, exclusive at expiry, nonregressing and never refreshed on conflict.
Core authentication necessarily performs its own controlled user/session reads;
"before private reads" here means before protected settings/safety context reads.
Consumption authenticates/validates the exact nonce before private target/state
reads, derives existing UUID from fixed storage and rejects a command UUID mismatch.
Recheck after observations and before each actual write attempt.

Allow only `upgrade_closed`, `begin_disable`, `abandon_closed` and independent
`receipt_read`, with the earlier confirmations/envelope fields. The only target
delta is an existing Boolean `auto_scan_enabled: true -> false` in the fixed
settings option. No posted option/table/target/key, arbitrary patch, enable,
grant/rebind/activate/dispatch/rollback/finish purpose or callback. Already false
is a fresh matching-context/null-pending no-op, not an epoch renewal. Retained
same-ID/digest/domain observation precedes new-mutation context checks; changed
intent conflicts. Expired command consumption denies; a fresh receipt intent can
observe it without replay. Historical pairing is not required to close/reconcile;
this does not create a replacement binding or grant eligibility.

The same owner privately creates a stack-scoped, one-use transaction continuation
only after exact durable begin read-back and a final fresh auth/nonce/window check.
It is bound to original intent, existing site/binding, exact post-begin snapshot,
pending/reserved IDs, connection identity and deadline. No public real equivalent
of `within_fixture(array, callback)` may mint it from data. A pure transition plan
or test-created real-shaped record is data, never such a handle. Invalidate it in
`finally`, including on denial/throw/unknown commit; no refresh, retained reuse or
cross-request serialization. Role/session changes after the final check remain a
residual race: row locks do not atomically lock WordPress authorization.

## Real-domain storage candidate, not fixture promotion

Refine the older schema-7 allocation: 7 now has an implemented fixture-specific
validator; reserve **8** for the new real candidate to avoid ambiguous same-version
acceptance. No current reader is changed. Root keys stay exactly `schema_version`,
`generation`, `enrollment_binding`, `schedule_revision`, `claims`, `authority`,
`dispatch`, `lifecycle`, `legacy_writer`, `writer`; schema_version is integer 8.
Preserve protected fields/history, authority false, consent false and disabled
lifecycle. Do not turn schema 8 into an accepted schema-3 observer/dispatcher input.

`legacy_writer` and `writer.origin` preserve the same finite exact typed schema-6
reconstruction defined earlier: complete frozen barrier, original generation,
schedule revision, permission generation, changed-at and source digest. Validate
that reconstruction with unchanged schema-6 rules. No recursive successor archive
or archival provenance promotion. Strict existing schema 6, null pending and no
unfinished protected work are the only upgrade source. Reject missing/corrupt/
autoloaded rows, older schemas, every schema-7 fixture successor and changed source
without repair. No schema-7-to-8 converter, relabel, reset or delete is proposed.

Writer keys remain exactly `source`, `origin`, `upgrade`, `authenticated_grant`,
`authenticated_receipts`, `internal_receipts`, `fixture_receipts`, `pending`,
`closure`, `completion`. Source is `closed_writer_admission_v1`. Grant is null;
new fixture_receipts is empty. New authenticated upgrade/begin/abandon records
use `authenticated_closed_writer_v1`; only owner-constructed terminal
`complete_disable` uses `internal_closed_writer_v1`. Historical fixture receipts
remain only in the frozen legacy group. Record keys stay `domain`, `purpose`,
`command`, `request_digest`, `result_generation`, `committed_at`, `completion_id`.
Current slots and archived maps cannot duplicate a record/ID or mix domains.

Use the earlier exact pending fields and terminal command shape; a begin reserves
one internal completion UUID once before retries, never accepts it from a form or
reallocates it after uncertainty. Completion must match original begin/site/
binding/closure epoch, reserved ID, original lifetime and derived after digest;
abandon has its own fresh authenticated command, not that reserved internal ID.
Keep the original reservation unavailable for reuse even after abandon. Validate
a contiguous monotonic receipt chain across all new current/history slots, all
three counters and nonregressing times; reject cross-domain/legacy collisions.
Pure validators certify shape/consistency only, not historical authentication.

Retain the combined 50 optional-history budget across legacy/authenticated/internal
records, 128 KiB state, JSON depth 16, 1024 bytes per new record and 4096-byte
minimum pending/closure reserve. Measure maximal real-domain records rather than
copying fixture measurements. Reserve four increments before upgrade, three before
begin and two before terminal as in the closed model. Exhaustion denies; no pruning,
counter reset, budget increase, invented receipt or expired-pending cleanup.

## Bounded serialized-target contract

Candidate codec identity is `php_settings_disable_v1`, fixed by construction and
included in context hashing, not a posted format choice. Input is the existing raw
settings row, at most 1 MiB, non-autoloaded (`no`, `off`, `auto-off` only). Safety
row has the same non-autoload requirement. Reject absent rows, unknown markers or
missing/malformed UUID or scan Boolean; do not call `Settings::get()`, `defaults()`,
`site_uuid()`,
`sanitize()`, `update()`, `maybe_install()` or `get_option()` to infer missing facts.
Do not call option/serialization hooks under a lock.

Choose a bounded, non-instantiating **primitive serialized-array parser**, not
`unserialize()`, `maybe_unserialize()` or JSON conversion of the option. Accept
only canonical `N`, `b`, `i`, `s` and `a` tokens, with a top-level array; integer or
string keys, no duplicate keys or PHP-key-coercion collisions; valid bounded
length/count syntax, native-range integers, depth at most 16 and at most 4096
value/key tokens combined. Reject objects/custom serialization/enums, references,
floats, malformed/trailing data, oversized declared lengths/counts, overflow and
unsupported tags before constructing the corresponding value. Strings are
byte-counted; supported text is valid UTF-8 and preserves its exact bytes. Do not
normalize/reorder/drop unknown ordinary fields. Unsupported legacy settings stay
closed/unresolved; no repair or compatibility fallback.

Require existing canonical lowercase UUID and literal Boolean scan field. Retain
the byte span of that root Boolean token; the only after-image replaces `b:1;`
with `b:0;`. All other original bytes, including ordering, integer/string types,
unknown fields, paths and token strings, remain **byte-for-byte** unchanged. Reject
if reparsing the bounded after-image differs in any other field or violates the
same limits. No reserialization of a normalized whole settings array and no
credential rewrite. Already false retains the original bytes as a no-op.

The codec's candidate result is private: fixed codec identity, existing UUID,
enabled Boolean, before/after digests and bounded after bytes. The parse tree is
not a public request result. After bytes are available only to the trusted owner,
never serialized into safety receipts, diagnostics or a response. Invalid input
returns a fixed redacted failure, not decoder exceptions or offending fragments.

Context version binds fixed blog/UUID/target/writer/codec, historical binding,
original permission epoch, source-state consistency digest and exact before/after
byte digests. Recompute at issuance/consumption and under locks; validate expected
post-begin state rather than requiring equality with pre-begin whole-state hash.
Full settings bytes contain secrets: keep them process-private only. Never persist
raw target/parsed credentials or export requests, nonce, cookie, session or target
digests through logs/status/support. Digests are private consistency/correlation
metadata, not signatures or secret-free public evidence. No new secret/key is
created by this design.

The PHP manual explicitly warns against treating `allowed_classes` as a safe
untrusted-input boundary; the narrow parser choice is a design inference, not an
implemented secure-parser claim. [PHP unserialize reference](https://www.php.net/manual/en/function.unserialize.php).
Core `get_option()` performs caching/filtering and unserialization, so it is not
the required raw-row provider. [WordPress get_option reference](https://developer.wordpress.org/reference/functions/get_option/).

## Transaction, cache and effective-state policy

The eventual backend must fix trusted current-site table/option identities and a
single verified primary native connection, prepare values and allowlist identifiers.
Do not reinterpret the existing wpdb CAS as paired/non-reconnecting storage. No
caller-provided DSN, database, port or credential; no separate credential changes.
Connection/SSL/socket/charset/engine details require supported-environment proof;
there is no generic DB_HOST parser or silent fallback approved here. Initial
support requires both rows in InnoDB, no nested transaction, routing/read replica,
automatic reconnect/restart or unreviewed db/cache drop-in. Reject unsupported
storage/cache environments rather than promise atomicity from a Boolean flag.

At most three actual upgrade/begin comparisons retain original intent and reserved
ID, each freshly guarded. Durable begin is a separate confirmed closed commit,
not target success. Unconfirmed/false/throwing begin acknowledgement stops target
work and reconciles the original ID. Freshly authenticate outside locks, then
lock safety first and fixed settings second on the same connection; revalidate
strict schema, exact pending/epoch/identity, original deadline and locked bytes.
No auth/option hooks, HTTP, logging, cron, queue, upload or callbacks under locks.
Conditionally stage only the Boolean byte patch and internal completion/removal of
that pending owner, recheck pure original clock/window, then commit the pair. A
clock tick that invalidates a prepared timestamp aborts rather than retimestamps;
no frozen clock, setup retry or implicit refreshed intent is runtime policy.

Fresh abandon uses the same locks and one original-epoch attempt. It records only
verified original before/after facts and advances fencing; it never writes the
target. Missing/unexpected target stays unresolved, not forced recovery. Paused
old writer, target ABA, timeout/deadlock, failed write/COMMIT or response loss may
not replay/reissue work. Definitive rollback retains the separately committed
begin. Unknown COMMIT remains unresolved until fresh authorized receipt and raw
target observations agree; a read failure is not proof of no effect. Recheck
response authorization after unlock; loss denies/redacts without erasing evidence.

Cache policy is deliberately **raw-authoritative with no cache-based admission**.
After confirmed commit, invalidate safety/settings individual keys plus
`alloptions`/`notoptions`; never publish a guessed or pre-commit value. Deletion
alone is insufficient: a racing old reader can repopulate stale data, and the
current settings helper explicitly sets cached values. Every supported consumer
of the scan bit must use the reviewed raw provider/fence; every whole-option and
identity writer must participate in the epoch/lock protocol. Do not install a
global option filter to bypass this work. External/persistent caches and custom
drop-ins remain unsupported until separately proven. Cache invalidation failure
does not roll back an already committed target or justify replay; it leaves
effective-state/coherence unverified and blocks production readiness. [WordPress cache deletion reference](https://developer.wordpress.org/reference/functions/wp_cache_delete/).

Private responses distinguish closure observation from target `not_attempted`,
`unchanged`, `committed`, `abandoned` or `unresolved`; only confirmed paired storage
and raw read-back can support `committed`. This means the stored Boolean changed,
not that scheduled/started scans, queued items, uploads or remote effects stopped.
Dispatch/execution remain false. Legacy Cron's next init can clear events after a
false setting: that later schedule mutation is not part of a storage-only proof
or approved by this design. Production wiring stays blocked until those effects,
all entry points and lifecycle behavior have their own approved integration.
