## Genuine-request closure: three different claims

| Layer | What must actually run | What it cannot establish |
| --- | --- | --- |
| Isolated APIs (existing) |real guarded methods and actual join against doubles; discriminating positives/guard mutants |genuine auth, credential/session validity, SQL, HTTP/SAPI or installed graph |
| Genuine core request/provider (future owned proof) |stock credential/cookie/session validation establishing the user, then genuine capability and action nonce, exact owned record, same-observation view/revision and actual conditional save through the join |public factory/wiring or FPM/HTTP behavior if the driver is CLI/private request DATA |
| Actual web/target eligibility (separately approved) |real selected web request path, runtime/source/observer/cache profile and intended same-observation form/POST/result behavior |arbitrary stacks, undeclared transports or release/deployment authority |

Setting a current-user ID manually is useful authorization/nonce setup, NOT
authentication proof. A true auth claim needs actual stock session/credential
validation, plus tampered/expired/wrong-user/session negatives. Never replace
current_user_can/wp_verify_nonce or assert an HTTP status as the only positive.
An actual positive must reach a physical acknowledged policy change and preserve
non-target bytes/autoload. Keep partial claims labeled if one layer is absent.

The owner's current manifest does NOT pin the complete authentication dependency
graph: capabilities/pluggable/user/roles/session implementation and their actual
conditional includes are not covered merely by Trusted_Source's database/cache
library pins. Before a future genuine proof, audit and freeze the selected pinned
core's complete ACTUAL auth include/callback/storage closure and effect costs in
the owning proof image. No guessed file list/hash/function behavior, full installed
bootstrap substitution or fixture-learned hash promoted to a runtime grant.
Reuse the existing trusted process/WordPress authentication model; do not invent
a parallel auth service or move private owner/config capture before authorization.
Unknown installed auth overrides/observer/cache graphs need explicit eligibility,
not silent callback removal, whole-bootstrap containment or new attestation tools.

Required future request evidence, with owned disposable users/roles/session storage,
site records and policy rows ONLY under separate exact lab/site approval:

1. Valid authenticated capable user + correct action nonce + exact record drives
   Guarded_Entry→Lazy_Provider→genuine initializer→view/save/no-op/conflict. Mode
   and revision come from the SAME authoritative view; no stale filtered display.
2. Anonymous/invalid session, authenticated user lacking manage_options, wrong
   action/user/session/expired/malformed nonce, compound/overflow/padded IDs,
   malformed/missing revision and mismatched/missing record deny in exact order.
   No owner source/config/credential capture, native allocation or policy read/write
   before admission. Necessary core authentication/user/role reads are separately
   attributed and bounded; do not falsely claim all WordPress auth performs zero SQL.
3. Observe the real owned owner's bootstrap/progress/query counters and physical
   policy state without replacing native/auth APIs. Source-backed mutations of
   each required guard and an always-unavailable provider must kill assertions,
   not launcher/parse failures. No fake ready/facts/handles or artificial success.
4. Fresh rows for stale same-/cross-site revisions, competing creation, genuine
   binary/length-sensitive CAS, post-submission uncertainty and no retry/rebase;
   preserve once-only effects and private cache/ambient registrations. Distinguish
   intervening-writer observations from simultaneous contention/transaction proof.
5. Nonces are intent, not capabilities, state revisions or one-use tokens. The
   revision is state-equivalence (including possible M→N→M), not a durable generation
   or authentication token. One provider instance is single-use; no new persisted
   anti-replay ledger is selected. All terminal secret references/owned resources
   and held-live/post-exit release need independent verification.

Private proof Reflection may compose handle-free fixtures and inspect progress,
but is NOT proof of a production builder. Before application integration, the
fixed code-owned construction/handoff must be implemented/tested with ordinary
PHP visibility, not copied Reflection or nonexistent cross-class private calls.
Public factories remain unavailable now. Do not claim public provisioned facade
or endpoint coverage from method-level fixture composition.
