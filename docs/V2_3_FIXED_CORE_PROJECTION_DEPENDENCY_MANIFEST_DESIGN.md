## Decision and evidence boundary

Retain the strict protected-value contract and Unsupported ordinary profiles.
The prior owned projection earned eight safe cached keys and thirteen real engine
permission denials, but both genuine cold-core branches stopped BEFORE executing
the next `wp_attachment_pages_enabled` read. That is a new required read, not an
authentication failure, completed bootstrap or reason to relax the query observer.

Select one fixed, test-only successor candidate: the same owned projection plus
exactly that ninth option, with separately bounded synthetic values. This document
does NOT add the key to the worker, view, fixture or effective privileges. A design
candidate identifier is not a profile seal, owner availability bit or authority.
Do not build another generic profile framework instead of obtaining core evidence.

The [official attachment-page change](https://make.wordpress.org/core/2023/10/16/changes-to-attachment-pages/)
documents the option's introduction in WordPress6.4 and values0/1. This establishes
its public meaning, NOT its precise caller graph or safety on the installed7.1.2
source. The exact source identity and caller/default behavior must be audited in
the separately approved owned proof before implementing the candidate. No LocalWP
core files were inspected in this design; the recorded blocked read is the local
observation. Do not infer that nine options suffice for all of wp-settings.php.

## Version and branch qualification

Exact core version AND inspected source identities are required; a version string
or successful receipt alone is insufficient. For the recorded7.1.2 candidate,
review the new option's actual caller, absent-value/default path and possible
writes, plus remaining bootstrap dependencies, before one fresh bounded attempt.
The ninth key is a candidate, not proof that no other dependencies exist.

WordPress6.0 remains unexecuted/Blocked. The documented6.4 introduction does not
prove the complete6.0 query/cache graph. No implicit download/install, minimum-WP
increase or reliance on a6.2-only cache shortcut. A later available6.0 runtime
requires its own reviewed exact-source branch; unknown versions are Unsupported,
not matched by a broad version range or automatically assigned nine keys.

Use fresh genuine nonpersistent cold cache for each autoload/fallback and0/1
fixture branch; retain populated canaries under varied autoload states. Record
actual attempted/completed safe queries, exact returned key/value membership and
cache provenance separately. A positive must contain the expected safe fixture
values, not just a count or passed=false from an always-unavailable owner.
An absent newly-required value must not become a fabricated success via a warm
cache, pre_option/pre_wp_load_alloptions shortcut, fake core, SHORTINIT or an
installation bypass. A genuinely absent optional read is allowed only after its
exact source/default behavior has been reviewed; it cannot authorize a write.

Keep DB enforcement independent: limited invoker, locked SELECT-only definer,
observer-free safe-read/real denial controls, and deliberate owned unsafe-view
assertion kill followed by verified revocation. Neither the query observer nor
PHP cache filtering is the primary protected-value boundary. No application base
table, real user/session, ledger/safety participant, FILE/routine or writer handle.

Preserve owner initial10s/root20s and outer HTTP1000/2000/4000/10000ms offsets.
No reset after manifest checks or preflight. Preserve existing statement, process,
pipe/output and cleanup bounds; do not enlarge them to accommodate another key.
If completion cannot fit, stop at a resource/design blocker. No HTTP listener,
content loader, admission bridge, grant, activation or rollback experiment here.
